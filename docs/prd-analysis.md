## 3. 해결할 문제

### 현재 운영 방식 (전부 수작업)
Google Forms 신청 → 입금 문자 확인 → 운영자 수기 매칭 → 네이버 예약 → 행사 2일 전 카톡 단체방 생성 → 1일 전 리마인드 → 식사 → 대화 콘텐츠 제공 → 개인별 피드백 → 다음 매칭에 참고

### 참가자 문제
- 신청 후 결제·매칭·확정 상태를 알기 어렵다
- 환불하려면 운영자에게 계좌를 직접 보내야 한다
- 매칭 실패 시 다른 날짜·지역 재신청이 번거롭다
- 이전 만족도가 다음 매칭에 반영되길 원한다

### 운영자 문제
- 신청·입금·단체방·식당 예약을 일일이 수기로 처리
- 다중 조건 수기 매칭의 부담과 누락 위험이 신청자 수에 비례해 증가
- 피드백과 만남 이력이 흩어져 다음 매칭에 반영하기 어렵다
- CS 자동화 필요

## 4. 제품 운영 원칙 (설계 판단 기준)

1. **정상 흐름은 운영자 개입 없이 끝난다.** 마감 시 자동 매칭 → 자동 재배치 → 자동 확정 → 자동 안내
2. **운영자는 예외만 처리한다.** 결제 오류, 식당 부족, 해결 안 된 조건 충돌, 신고·안전
3. **필수 조건은 절대 완화하지 않는다.** 억지로 테이블을 만들지 않는다
4. **이동·보관·환불은 참가자가 선택한다.** 시스템이 임의로 결정하지 않는다
5. **매칭 결과는 설명 가능해야 한다.** 확정·재배치·실패 사유를 참가자·운영자에게 보여준다 (타인 개인정보·상세 점수는 비공개)

## 6. 매칭 규칙 정리

### 필수 조건 (하나라도 위반 시 확정 불가 → 재배치)
- 결제 완료
- 참가 가능 날짜·희망 지역 일치
- 한 테이블 4~6명
- 최고령자와 최연소자 나이 차 8살 이내
- 차단·신고·비선호 관계 없음

### 선호 조건 (점수 합산, 우선순위 순)
1. 성비
2. MBTI 궁합
3. 공통 관심사
4. 만나고 싶은 사람의 성향
5. 새로운 사람 비율 (이전 만남 최소화)

### 자동 확정 기준
필수 조건 전체 충족 + 운영자 설정 최소 매칭 점수 이상

### 재배치 우선순위 (PRD 7.4)
1. 같은 날짜 · 같은 지역의 다른 미확정 테이블
2. 같은 날짜 · 선택한 다른 지역
3. 선택한 다른 날짜 · 같은 지역
4. 선택한 다른 날짜 · 다른 지역
5. 미선택 회차 추천 (동의 후 이동)
6. 이용권 보관 또는 환불 선택

### 주목할 엣지 케이스
- **후보군 7명**: 4~6인 테이블로 완전 분할 불가 (6+1, 4+3). 8명 이상은 항상 분할 가능
- 나이 차 때문에 같은 날짜·지역 안에서 고립되는 인원
- 차단 관계 때문에 조합 수가 급격히 줄어드는 경우
- 매칭을 두 번 실행했을 때 중복 테이블 생성 여부
- 확정 후 1명 취소 → 대기자 충원 또는 남은 인원 재배치

## 7. 운영 정책

### 이용권 (CTO 자료 03 기준)
| 이용권 | 가격 |
|---|---|
| 1회권 | 9,900원 |
| 1개월 멤버십 | 35,000원 |
| 3개월 멤버십 | 75,000원 |
| 6개월 멤버십 | 120,000원 |

> PRD는 "1회권 또는 구독 이용권"으로만 표현. 멤버십의 사용 횟수 규칙(월 몇 회인지)은 미정.

### 환불·취소·노쇼 정책
- 진행 2일 전 이후 환불 불가
- 당일 취소 및 단체 채팅방 퇴장 불가
- 결제 전 화면과 신청 완료 화면에서 정책을 반드시 보여줌 (PAY-02)
- 매칭 불가 시 환불은 예외: 참가자 선택 시 원결제수단으로 자동 환불 (PAY-03)
- 당일 취소·노쇼는 참석 상태와 이용 제한 검토 대상으로 기록

## 8. 비기능 요구사항 (PRD 16장)

- **개인정보**: 연락처·생년·차단·신고·사람별 선호는 운영상 필요한 사람에게만 공개. 매칭 전 타 참가자 정보 비공개, 확정 후에도 제한된 소개만
- **운영자 권한**: 권한별 접근 통제, 주요 변경 이력 기록
- **사용성**: 모바일 우선, 최초 신청 5분 이내 완료, 홈에서 현재 상태 즉시 확인, 실패·대기 상태에서도 다음 행동을 한 화면에서 선택
- **추적**: 매칭 버전·결과, 자동 처리 실패, 발송 성공·실패·재시도, 일정 이동·보관·환불 처리, 상태 변경 시각·주체 기록
- **내보내기**: 참가자 목록과 테이블 결과 CSV 내보내기

## 10. MVP 범위 판단

### P0 (반드시 시연 가능해야 함)
회원·프로필(ACC-01~05), 회차·신청·결제(APP-01~04, PAY-01~03), 상태·대체 일정(STA-01~06), 자동 매칭(MAT-01~13), 안내(INF-01~08), 대화 콘텐츠(CON-01~03), 피드백·안전·재방문(FDB-01~04, SAF-01~02, RET-01~02), 운영자 웹 필수 화면

### P1 (P0 완주 후 여유 시)
프로필 재사용(ACC-06), 실결제 연동(PAY-04), 대기자 자동 전환(STA-07), 운영자 긴급 수정(MAT-14), 가중치 설정(MAT-15), 콘텐츠 관리(CON-04), 이용권 관리(RET-03)

### P2 (이번 범위 제외)
학습형 추천(MAT-16)

### 모의 구현 허용 범위 (PRD 명시)
- 로그인: 테스트 계정
- 결제: 토스페이먼츠 테스트 모드 연동, 실패 시 Mock으로 전환
- 환불: 상태 전환 모의 구현

## 11. 완료 조건 (PRD 18장 · 시연 시나리오 기준)

1. 서로 다른 프로필의 테스트 참가자들이 날짜·지역을 선택하고 신청
2. 매칭 마감 시각에 결제 완료자 대상 자동 매칭 실행
3. 필수 조건과 우선순위에 따라 4~6인 테이블 생성
4. 4명 미만·조건 미충족 조합 해제 후 자동 재배치
5. 조건 검증 통과 테이블 자동 확정
6. 식당 자동 배정 및 앱 단체방 자동 생성
7. 참가자가 단체방에서 매칭 결과·식당·큐레이션·안내 확인
8. 미매칭자에게 대체 일정 추천, 이동 또는 환불 자동 처리
9. 행사 전 리마인드와 행사 중 대화 콘텐츠 자동 게시
10. 행사 후 체크인과 만족도·사람별 선호 입력
11. 다음 매칭에서 이전 만남과 피드백 반영 확인
12. 정상 시나리오는 운영자 개입 없이 완료, 미해결 예외만 운영자 화면에 표시

**시연 준비 필수 장치**
- 데모용 시간 제어 (마감·리마인드·행사 시작 시각을 앞당기는 기능)
- 시나리오별 시드 데이터 원클릭 투입
- 2회차 연속 시연으로 피드백 반영 증명
