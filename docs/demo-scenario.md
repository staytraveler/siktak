# 시연 시나리오 및 시드 데이터 (demo-scenario.md)

> 위치: `docs/demo-scenario.md`
> 기준: PRD v0.2 18장(해커톤 완료 조건), `docs/domain/matching.md`, `docs/domain/states.md`
> 작성: 2026-10-17 [기획]
> 목적: 심사위원이 **한 번의 데모로 12단계 완료 조건을 모두 확인**할 수 있게 한다.

---

## 0. 설계 원칙

1. **결과가 예측 가능해야 한다.** 시드 데이터는 매칭 명세(matching.md)대로 돌렸을 때 의도한 장면(분리, 재배치, 실패, 예외)이 반드시 나오도록 출생연도·회차 선택을 설계했다.
2. **심사위원이 기다리지 않게 한다.** 시각 기반 자동 처리는 어드민의 **데모 도구**로 시계를 앞당겨 실행한다. 자동 처리 로직 자체는 실제 스케줄러와 같은 코드를 쓴다.
3. **언제든 처음으로 되돌릴 수 있다.** "시드 초기화" 한 번으로 데이터와 시계를 초기 상태로 만든다.
4. 데모 도구는 `demo.enabled=true`일 때만 노출한다 (실서비스 전환 시 비활성화).

## 1. 데모 도구 (운영자 웹 `/admin/demo`)

| 버튼 | 동작 |
|---|---|
| 시드 초기화 | 전체 데이터 삭제 후 시드 재투입, 데모 시계 초기화 (T0 = 실제 현재 시각) |
| ⏩ J1 1회차 매칭 마감 | 시계를 S1·S2의 `match_run_at`으로 이동 → 스케줄러 즉시 실행 |
| ⏩ J2 S3 매칭 마감 | 시계를 S3의 `match_run_at`으로 이동 |
| ⏩ J3 행사 1일 전 | 리마인드 발송 시점으로 이동 |
| ⏩ J4 행사 시작 | 대화 콘텐츠 게시 시점으로 이동 (체크인 가능) |
| ⏩ J5 행사 종료 | 노쇼 후보 표시, 피드백 요청, 만남 이력 생성 |
| ⏩ J6 2회차 매칭 마감 | 시계를 S4·S5의 `match_run_at`으로 이동 |
| 체크인 일괄 (시연용) | 1회차 확정자 중 `user13`을 제외한 전원 체크인 |
| 피드백 일괄 (시연용) | 체크인한 참가자 중 아직 피드백 없는 사람에게 기본 피드백 입력 |
| 2회차 신청 투입 | 1회차 S1 참석자 전원 + 신규 2명(`user25`, `user26`)이 S4에 신청·결제 완료 |

> 시계 이동은 `settings.demo.clock-offset` 값만 바꾼다. 서버 코드는 `Clock` 빈을 통해서만 시각을 읽는다 (CLAUDE.md 6장).

## 2. 회차·지역·식당 시드

**기준 시각**: 시드 초기화 시각을 `T0`, 1회차 행사일을 `D = T0 + 3일`로 둔다.

### 회차
| 회차 | 지역 | 행사 시작 | 매칭 실행 (`match_run_at`) | 용도 |
|---|---|---|---|---|
| S1 | 성수 | D 19:30 | D−2일 12:00 | 1회차 메인 (분리·차단 분리·재배치 도착지) |
| S2 | 홍대/합정 | D 19:30 | D−2일 12:00 | 7명 → 1명 연령 이탈 → 재배치 출발지 |
| S3 | 성수 | D+1일 19:30 | D−1일 12:00 | 인원 부족 실패 → 대체 일정 장면 |
| S4 | 성수 | D+7일 19:30 | D+5일 12:00 | 2회차 (피드백 반영 확인) |
| S5 | 강남 | D+7일 19:30 | D+5일 12:00 | 대체 일정 이동 도착지 |

모든 회차: 정원 30, 신청 마감 = `match_run_at`, 2시간 행사.

> 매칭 실행을 행사 2일 전으로 둔 이유: 현재 운영 방식(2일 전 단체방 생성)과 환불 기준일(2일 전)이 같은 시점이라 정책 설명이 단순해진다.

## 5. 12단계 시연 흐름

심사위원 기준 소요 시간 약 15분. 화면은 참가자 앱(모바일)과 운영자 웹을 나란히 띄운다.

| 단계 | PRD 18장 | 조작 | 확인할 화면 | 확인 포인트 |
|---|---|---|---|---|
| 1 | 테스트 참가자들이 날짜·지역을 선택하고 신청 | `demo01` 로그인 → S1 신청 → 1회권 → 토스 테스트 결제 | 참가자 홈 | 상태가 "결제 완료 · 매칭 대기", 매칭 예정 시각 표시 / 어드민 신청자 목록에 시드 25명 + demo01 |
| 2 | 매칭 마감 시각에 자동 매칭 실행 | 데모 도구 **J1** | 어드민 자동 매칭 모니터 | `MatchRun` 1건 생성, 운영자가 시작 버튼을 누르지 않음 |
| 3 | 필수 조건·우선순위로 4~6인 테이블 생성 | — | 매칭 모니터 → 테이블 상세 | S1 3개·S2 1개 테이블, 연령 범위·성비·MBTI·공통 관심사·점수 표시, user05/06 분리 |
| 4 | 4명 미만·조건 미충족 해제 후 자동 재배치 | — | 매칭 모니터 → 배치 로그 | user15: S2 `AGE_GAP` → S1 재배치(2단계) / user14: `DEFERRED` 대기 복귀 / user16: 미결제 제외 |
| 5 | 검증 통과 테이블 운영자 승인 없이 자동 확정 | — | 매칭 모니터 | 전 테이블 `CONFIRMED`, 확정 주체 `SYSTEM`, 상태 이력에 운영자 개입 없음 |
| 6 | 식당 자동 배정 · 단체방 자동 생성 | — | 테이블 상세 · **예외 처리함** | 테이블별 식당·예약명·단체방 생성 / S1 테이블 1개 `VENUE_UNAVAILABLE` 예외 → 운영자가 그린키친 수용량 추가 후 재배정 |
| 7 | 단체방에서 매칭 결과·식당·큐레이션·안내 확인 | `demo01` 참가자 앱 | 매칭 확정 화면 · 단체방 | 식당 카드, 집합 시간, 매칭 근거(공통 관심사·연령대·성비), 취소 정책 공지. 다른 참가자 상세 정보·점수 비노출 |

## 7. 대화 콘텐츠·알림 시드

### 대화 콘텐츠 (`conversation_contents`)
- 관심사 10종 × 주제 2개 = 20개 (`TOPIC`, `tags`에 관심사 코드)
- 아이스브레이킹 5개 (`ICEBREAKER`, 공통)
- 테이블 공통 관심사 상위 3개에서 주제 1개씩 → 부족하면 일반 주제로 채워 **최소 3개** (CON-02)

### 알림 템플릿 (`notification_templates`)
PRD 14장 시점별 1개씩: `APPLICATION_SUBMITTED`, `PAYMENT_PENDING`, `PAYMENT_PAID`, `REALLOCATING`, `MATCH_CONFIRMED`, `MATCH_FAILED`, `TRANSFERRED`, `REFUND_REQUESTED`, `REFUND_COMPLETED`, `REMINDER_D1`, `FEEDBACK_REQUEST`, `NEXT_SLOT_RECOMMEND`

## 8. 시드 구현 메모 (Claude Code용)

- 시드는 `demo-v1` 시나리오 하나로 관리하고, 데이터는 코드(또는 JSON 리소스)로 고정한다.
- 출생연도·회차 선택·차단 관계는 **이 문서의 값을 그대로** 쓴다. 바꾸면 4장 예상 결과가 깨진다.
- 표에 없는 프로필 값(직업, 가격대, 대화 스타일 등)은 임의로 채워도 된다.
- 4장 예상 결과를 검증하는 **통합 테스트**를 만든다 (시드 투입 → J1 → J2 → J6 순서로 실행 후 결과 비교).
- 시드 초기화는 운영 DB가 아닌 데모 환경에서만 동작하도록 `demo.enabled`로 막는다.
