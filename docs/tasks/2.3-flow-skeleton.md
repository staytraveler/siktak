# 2.3 전체 흐름 가짜 로직 연결 (워킹 스켈레톤)

> 아젠다: 2. 워킹 스켈레톤 · 마감 10/17
> 담당: V1 (`siktak`, 브랜치는 `feat/flow-skeleton` → 완료 시 main 머지·push)
> 참조: `docs/erd.md`, `docs/domain/states.md`, `CLAUDE.md` 6·9장, `docs/demo-scenario.md` 2장
> PRD: APP-01~03, PAY-01, STA-01, MAT-01(가짜), INF-04, FDB-02 (모두 얇게)

## 목표
**신청 → Mock 결제 → 단순 매칭 → 확정 → 단체방 메시지 → 피드백 저장**이 로컬과 배포 환경에서 끝까지 한 번 이어진다.
화면·로직은 얇게. 핵심은 **실제 스키마·상태 전이·감사 로그 구조를 이번에 제대로 깔아서** 이후 작업이 그 위에 살만 붙이게 하는 것.

## 블레이버스 태스크
- [ ] 회차 생성·조회 API 및 화면
- [ ] 신청·Mock 결제 흐름 연결
- [ ] 단순 매칭 및 확정 처리
- [ ] 단체방 메시지·피드백 저장 연결

## 작업

### 0. 공통 (먼저)
- 공통 에러 응답 `{code, message, details}` + `@RestControllerAdvice` + 테스트 (V1 제안 반영)
- 임시 인증: 이번엔 JWT 없이 요청 헤더 `X-User-Id`로 사용자 식별 (3.1에서 JWT로 교체). 이 사실을 코드 주석과 `decisions.md [CC]`에 남겨라.

### 1. 스키마 (Flyway V2)
`docs/erd.md` 기준으로 아래 테이블을 **컬럼까지 ERD대로** 만든다. 이번 흐름에 안 쓰는 컬럼도 ERD에 있으면 넣는다(나중 마이그레이션 최소화).
- `users`, `profiles`, `regions`, `event_slots`, `applications`, `application_slot_choices`, `payments`, `user_passes`
- `match_runs`, `dining_tables`, `table_members`, `match_placement_logs`
- `chat_rooms`, `chat_members`, `chat_messages`, `feedbacks`
- `status_histories`, `settings`
- 제약·인덱스는 ERD 4장대로 (부분 유니크 포함).
- 나머지 테이블(venues, notifications, exception_cases 등)은 해당 기능 작업에서 V3 이후로 추가.

### 2. 상태 전이 기반
- 4개 상태 enum을 PRD 12장 그대로.
- **상태 전이 서비스**: 허용 전이표(`states.md`) 밖의 전이는 예외. 전이마다 `status_histories`에 transition_code·actor·reason 기록. 이미 목표 상태면 no-op.
- 이번 흐름에서 쓰는 전이만 구현: A1·A2, P1·P2, M1·M2·M3, (참석 T1은 이번엔 생략 가능)
- 상태 전이 서비스 단위 테스트 (허용/거부/no-op/이력 기록).

### 3. 흐름 (API + 최소 화면)
| 단계 | API | 화면 |
|---|---|---|
| 회차 | 어드민 `POST/GET /api/v1/admin/slots`, 참가자 `GET /api/v1/slots` | `/admin/slots` 생성 폼+목록, `/app` 목록 |
| 신청 | `POST /api/v1/applications` (회차 복수 선택, priority 순) → A2 + P1 | `/app`에서 회차 체크 → 신청 |
| Mock 결제 | `POST /api/v1/applications/{id}/payments/mock-approve` → P2 + M1. `PaymentGateway` 포트 + `MockPaymentGateway` (CLAUDE.md 8장) | 신청 상세에 "결제(테스트)" 버튼 |
| 단순 매칭 | 어드민 `POST /api/v1/admin/slots/{id}/run-matching` → WAITING을 신청순 4~6명씩 묶어 `dining_tables`·`table_members` 생성, M2→M3. `match_runs` 1건 기록. **가짜 로직임을 이름에 명시** (`SimpleSequentialMatcher`) | 어드민 회차 상세에 버튼 + 결과 테이블 목록 |
| 단체방 | 확정 시 테이블당 `chat_rooms` 1개(멱등), 멤버 초대, 시스템 메시지 1개("테이블이 확정됐어요") | `/app` 내 신청 상세 → 단체방 메시지 목록 |
| 피드백 | `POST /api/v1/feedbacks` (테이블 분위기·대화·식당 1~5) | 단체방 화면 아래 간단 폼 |
| 상태 | `GET /api/v1/me/applications` → 4개 상태 각각 반환 | `/app` 홈에 상태 표시 |

- 사용자는 이번엔 시드 3~6명(`user01`~)을 V2 마이그레이션이 아닌 **개발용 시드 SQL/러너**로 넣고, `/app`에 사용자 선택 드롭다운(헤더 `X-User-Id`)을 둔다. 정식 시드·데모 도구는 2.4.

### 4. 경계
- **`com.siktak.matching.domain.engine`은 V2 영역. 건드리지 마.** 가짜 매칭기는 `com.siktak.matching.application`(또는 `infra`)에 두고, 나중에 V2 엔진으로 교체할 수 있게 인터페이스 하나(`TableMatcher` 등) 뒤에 둔다.
- 스케줄러는 만들지 않는다 (2.4·4.5). 매칭은 어드민 버튼으로만.
- DB 절전 원칙(decisions.md) 유지.
