# 4.4 매칭 엔진 운영 연결 (DB·상태·식당 배정·예외)

> 담당: **V2** (`siktak-matching`, `feat/matching-engine` 이어서)
> 참조: `docs/domain/matching.md` 5·7·11장, `docs/domain/states.md` 3·4장, `docs/erd.md` 3-4·3-5·3-8, `docs/demo-scenario.md` 2·4장
> PRD: MAT-07·08·10·11·12·13, INF-02, STA-03·04, 15장

## 목표
V1이 만든 가짜 순차 매칭(`SimpleSequentialMatcher`)을 **V2 엔진으로 교체**하고, 확정·재배치·실패·식당 배정·예외까지 **DB와 상태 전이로 끝까지** 연결한다.
→ 데모 도구에서 J1을 누르면 `demo-scenario.md` 4장 "J1 후" 결과가 **실제 DB에** 그대로 생겨야 한다.

## 0. 시작 전 (중요)
- **`main`을 네 브랜치에 머지**해. 2.3(스키마 V2, 상태 전이 서비스, `TableMatcher` 포트, 단체방)이 들어 있다.
- V1이 지금 2.4(데모 시계·작업 실행기·demo-v1 시드)를 하고 있고, 2.4 0번에서 네 브랜치를 main에 머지한다. 둘이 같은 파일을 만지지 않도록:
  - **마이그레이션 번호: 너는 `V3__`, V1은 다음부터 `V4__` 이후.** (V1에게도 전달함)
  - V1 영역: `common`, `slot`, `application`, `payment`, `chat`, 시드·데모·스케줄러(`ScheduledJobRegistry` 등). 너는 이 패키지의 **기존 파일을 수정하지 말고**, 필요한 경우 새 클래스를 추가하거나 `v2-to-pm.md`로 요청해.
  - 너의 영역: `matching`, `venue`, `content`, 그리고 새로 만드는 `exception`(예외 큐) 패키지.

## 1. 스키마 V3
ERD대로: `match_resolutions`, `exception_cases`, `venues`, `venue_slot_capacities`, `conversation_contents`(테이블만. 투입은 아래 5번). 제약·유니크(`case_key` 등) 포함.

## 2. 엔진 어댑터
- `TableMatcher` 포트의 새 구현 `EngineTableMatcher`: DB에서 `MatchingInput` 구성(후보·선택 회차 priority·차단(`user_blocks`)·`AVOID`(`person_preferences`)·만남 이력(`user_encounters`)·설정 `settings.matching.*`) → 엔진 실행 → 결과 저장.
  - `user_blocks`·`person_preferences`·`user_encounters` 테이블이 아직 없으면 V3에 같이 추가해 (ERD 3-4·3-7 정의 그대로). 7.x에서 쓰기 기능이 붙는다.
- 설정으로 전환: `siktak.matching.engine=v2|simple` (기본 `v2`). 기존 가짜 매칭기는 지우지 말고 남겨둔다.

## 3. 저장·상태 전이
- `match_runs`: params 스냅샷, `algorithm_version`, summary. 멱등(run_key)은 기존 것 유지.
- `dining_tables`·`table_members`: 엔진 `ProposedTable` 그대로, `score_detail`·`summary`(PRD 7.2) JSON 저장.
- `match_placement_logs`: 엔진 `PlacementLog` 전부 (causeCode 포함, 컬럼 없으면 V3에 추가).
- 상태 전이 (V1의 `StatusTransitionService` 사용):
  - 최초 배치 확정 → M3 / 재배치 거쳐 확정 → M4 → M5
  - `deferred` → M4a (`WAITING` 복귀)
  - `failed` → M4 → M6 (`ALTERNATIVE_OFFERED`) + 1회권 결제면 P5 (`REFUND_AVAILABLE`) + `match_resolutions` 생성(4.2 `AlternativeSlotRecommender`로 추천 회차, `respond_by` = 원래 1순위 회차 행사일)
  - `excluded`: `NOT_PAID`는 상태 변경 없이 로그만, `ACCOUNT_RESTRICTED`는 `exception_cases`
  - 참가자 노출 문구는 matching.md 7-2 그대로 `applications.match_fail_reason`에.

## 4. 식당 배정 (확정 직후, 같은 트랜잭션 또는 바로 다음 단계)
- 4.2 `VenueAssigner` 사용. 결과를 `dining_tables.venue_id`·`reservation_name`·`venue_assigned_at`, `venue_slot_capacities.reserved_tables`에 반영.
- 예약명은 **처음 배정할 때 저장한 값을 재사용** (4.2 PM 확인 2번 답).
- 미배정 → `exception_cases(VENUE_UNAVAILABLE)`, `case_key`로 중복 방지. 테이블 확정 자체는 유지 (PRD 15장: 식당 실패는 운영자 예외, 매칭 결과는 유효).
- 운영자 재배정 API: `POST /api/v1/admin/tables/{id}/assign-venue` (수용량 늘린 뒤 다시 시도). 화면은 8.x에서.

## 5. 시드
- V1의 demo-v1 시드에 **식당·회차별 수용량(`demo-scenario.md` 2장)** 과 **대화 콘텐츠(4.2 JSON)** 를 추가한다. V1 시드 구조에 확장 지점이 있으면 거기에, 없으면 `VenueSeed`·`ContentSeed`를 만들고 V1에게 연결 요청(`v2-to-pm.md`).
- 가격대 코드는 matching.md 4장에 확정했다: `UNDER_20K`, `20K_40K`, `OVER_40K`. 시드 식당·프로필에 값 넣기 (프로필 값은 V1 시드 담당, 요청만).

## 6. 조회 API (화면은 8.x에서)
- `GET /api/v1/admin/match-runs`, `GET /api/v1/admin/match-runs/{id}` (summary + 배치 로그)
- `GET /api/v1/admin/tables/{id}` (구성·점수·요약·식당·단체방 id)
- `GET /api/v1/admin/exceptions?status=OPEN`
- 참가자 `GET /api/v1/me/applications/{id}/match-explanation` — matching.md 7-3 (다른 참가자 정보·점수 비노출)
